# Development test data

The local deployment uses synthetic course-completion data through the real
PostgreSQL data-provider plugin. It does not require a personal record or an
external issuer registry. These values describe the checked-in configuration;
they are not a new issuance or conformance result.

Run `python runner/setup.py` before tests or deployment. Secrets, signing keys,
wallet keys and TLS material are **generated by runner/setup.py**. Generated
configuration is local and must not be committed or copied into a submission.

## Synthetic course record

Source: [02-course.sql](../docker/certify-final-init/02-course.sql).

| Field | Non-secret development value |
|---|---|
| Table | `certify.course_completion` |
| subject_id | `11111111-1111-4111-8111-111111111111` |
| learner_name | `Development Learner` |
| course_id | `COURSE-DEV-001` |
| course_name | `Introduction to Digital Credentials` |
| completed_on | `2026-01-15` |

[certify-course.properties](../docker/certify-config/certify-course.properties)
selects `PostgresDataProviderPlugin` and maps scope `course_completion` to this
table using the authenticated subject ID. Issuance and expiry timestamps come
from the query rather than hard-coded credential evidence.

## Credential configuration

Source: [course_issuer.py](../runner/course_issuer.py), `configure`.

| Setting | Value |
|---|---|
| Configuration ID | `course-completion-sdjwt` |
| Credential type / vct | `urn:inji:development:course-completion:1` |
| Certify configuration format | `dc+sd-jwt` |
| Official suite credential-format variant | `sd_jwt_vc` |
| Scope | `course_completion` |
| Signature algorithm | `ES256` |
| Display name | `Development Course Completion` |

The format names above belong to different configuration interfaces; no protocol
translation is implied. The same source defines the template and selectively
disclosed course fields. Signing key material is generated by runner/setup.py.

## Clients, identity provider and endpoints

Client and realm definitions are generated from [setup.py](../runner/setup.py).
Defaults used by execution are in [run-conformance.sh](../run-conformance.sh)
and [run-clean-conformance.sh](../run-clean-conformance.sh).

| Item | Non-secret value |
|---|---|
| Identity-provider realm | `course` |
| Primary conformance client | `conformance-course-wallet` |
| Second conformance client | `conformance-course-wallet-2` |
| Separate issuance smoke client | `course-wallet` |
| Development login name | `development-learner` |
| Passwords, client secrets and private keys | generated by runner/setup.py |
| Issuer base | `https://host.docker.internal:8446` |
| Issuer metadata | `https://host.docker.internal:8446/.well-known/openid-credential-issuer` |
| Authorization server | `https://host.docker.internal:8446/auth/realms/course` |
| Native credential endpoint | `https://host.docker.internal:8446/v1/certify/issuance/credential` |
| Verify API base | `https://localhost:8445/v1/verify` |
| Native Verify request path | `/v2/vp-request` relative to the API base |
| Verify UI | `https://host.docker.internal:8445/verify` |
| Official suite | `https://localhost:8443` |

Login selectors and environment variable names are in
[course-browser.json](../config/course-browser.json). The verifier request body
is [verify-request.final.json](../config/verify-request.final.json).
Its suite-generated presentation credentials are distinct from local course
issuance. Combined execution does not establish course-to-verifier interoperability.

## Selected official plans

Source: [issuer template](../config/certify-oid4vci-config.json.template) and
[verifier template](../config/verify-oid4vp-config.json.template).

| Component | Plan |
|---|---|
| Certify | `oid4vci-1_0-issuer-test-plan` |
| Verify | `oid4vp-1final-verifier-test-plan` |

Issuer defaults are `credential_format=sd_jwt_vc`,
`client_auth_type=private_key_jwt`, `sender_constrain=dpop`,
`vci_authorization_code_flow_variant=wallet_initiated`,
`vci_credential_encryption=plain`, `vci_grant_type=authorization_code`,
`fapi_profile=vci`, `authorization_request_type=simple`,
`fapi_request_method=unsigned`, `fapi_response_mode=plain_response`,
`grant_management=disabled` and `openid=plain_oauth`.

Verifier variants are `vp_profile=plain_vp`, `credential_format=sd_jwt_vc`,
`client_id_prefix=redirect_uri`, `request_method=url_query` and
`response_mode=direct_post`. A POST-named module does not by itself prove that
request URI POST was exercised. POST and status-list interoperability remain
not verified; see [validation limits](VALIDATION.md).

# CI/CD execution and security

Ordinary hosted CI and live official conformance have separate acceptance criteria. Hosted run [39392516456](https://github.com/SantoshReddy0603/mosip-inji-conformance/actions/runs/39392516456) passed all five jobs on commit `797b02193479ac090768864793a078c4e0b0ae51`; all five artifacts were downloaded and validated. This is historical evidence, not proof that a later commit passed. The final submission validation report records the current commit and its actual run.

## Production releases and manual execution

`full-stack-conformance.yml` subscribes only to `release: published` and manual dispatch. It filters draft and prerelease releases. There is no tag-push subscription, avoiding duplicate tag/release executions; edits and draft creation do not run conformance. Manually dispatch only the repository default branch. A published production release uses GitHub's immutable event SHA, which is the tagged release commit. A disposable hosted authorization job checks the event, checks out that SHA and verifies default-branch ancestry before the live job is eligible. Live checkout uses the authorized SHA, never the moving tag or branch. Both jobs have only contents:read. Actions are pinned; checkout never persists credentials. Repository-wide live concurrency queues runs without cancelling active ones. Workflow changes are not deployed until approved for main.

The `inji-conformance` environment must have required reviewers and deployment rules allowing the default branch and approved production release tags. Configure these through Settings > Environments > inji-conformance. YAML does not create these protections. Review the exact commit's ordinary CI before approving live execution. Never assign the dedicated runner to PR workflows. Publication/merge/release and runner registration require owner approval; this implementation does not grant it.

## Runner feasibility and deployment modes

Existing reachable deployment (default): the live job uses disposable GitHub-hosted ubuntu-24.04. Docker is available, but services are not initialized or shut down by this mode because they belong to the supplied deployment. Set OIDF_URL, CERTIFY_ISSUER_URL, VERIFY_API_URL, VERIFY_UI_URL, CA_BUNDLE and real plan/browser configuration through repository Actions Variables (Settings > Secrets and variables > Actions > Variables). Wallet private JWK files must be provisioned securely on the runner at the configured paths; use an authorized secret-provisioning mechanism. Set the issuer login, OIDF token and S3 credentials only when the deployment needs them, in environment Secrets. S3_ENDPOINT and S3_BUCKET must point to an existing accessible automationtests bucket. Localhost URLs cannot reach this laptop from a GitHub VM. No password or token belongs in chat.

Managed synthetic development stack: set repository Actions variable INJI_MANAGED_LOCAL_STACK=true (Settings > Secrets and variables > Actions > Variables). Do not set this selector only at environment scope: GitHub must resolve runs-on before the runner declares its environment. Keep deployment mode consistent across job selection and steps. The job selects a dedicated self-hosted Linux x64 runner labelled inji-conformance with working Docker Desktop integration (for example WSL Ubuntu). The existing manifests publish loopback-only ports and use Desktop's host.docker.internal routing; native hosted Linux is not currently validated for this topology. This is a networking compatibility limit, not proof that hosted hardware cannot run the stack. GitHub documents private ubuntu-24.04 as 2 CPUs/8 GB/14 GB; the local engine has 16 CPUs and about 7.6 GiB. Measured twelve-container idle use was approximately 3 GiB, excluding Java builds, browser, caches and filesystem overhead. Do not infer peak build capacity from idle usage. Allow at least 8 GB Docker RAM and substantial disk for images, pinned source, Maven caches and private evidence; record actual free capacity before execution.

The managed job builds missing pinned images, extracts only tracked source into a fresh run-specific directory, generates new development secrets and keys, starts twelve real services and five fresh owned volumes, initializes the local artifact bucket, waits for readiness, configures actual Postgres-backed issuance, and invokes the existing parallel runner/report lifecycle. Images and dependency caches may be reused; data and keys are fresh. The shell trap and an always-run workflow step remove only ownership-verified isolated volumes. They do not delete historical stacks. Avoid other processes on ports 8443/8445/8446/9000/9001. Outbound access is required to GitHub/GitLab, container registries, Maven repositories and Python/browser downloads; inbound internet exposure is unnecessary for local suite development mode. No external issuer registry or personal data is needed.

Install a dedicated runner only after approval: repository Settings > Actions > Runners > New self-hosted runner; select Linux x64, follow GitHub's local registration commands and add label inji-conformance. Keep registration tokens local. Use an isolated workspace and Docker daemon for trusted jobs. The connector cannot register runners, change environment protections or dispatch workflows. Main currently requires separate merge approval; no live workflow run has been claimed.

## Execution, artifacts and honest failures

The live entrypoint performs readiness, real issuer/verifier plans, polling/exports, native module TestNG/Extent, consolidated reports, verified MinIO/S3 upload and strict gating. Restricted CI summaries upload after success or failure; raw screenshots, signed exports and credentials remain private. Managed infrastructure cleanup also executes after failure. An infrastructure failure and an official benchmark failure are different diagnoses. A six-REVIEW result must remain exit 1, never a green job. Request URI POST: **POST coverage not established.** Certification and OIDF contact are optional and are not assignment prerequisites.

Before the first live run, approve and merge the reviewed implementation into main and configure the chosen environment. Then Actions > Authorized live conformance release gate > Run workflow > main > combined exercises the pipeline without publishing anything. To test the automatic event, obtain separate approval, create a stable production release tagged at an already reviewed main commit, and publish once. Confirm the run's event=release, head SHA=tag commit, authorization job success, service/plan/report/storage logs and expected failed benchmark. Do not publish a test release without approval. Draft/prerelease filtering and ancestry/security contracts are tested locally; simulated payload tests are not actual release-event evidence.

GitHub variable timing reference: [Configuration variable precedence](https://docs.github.com/en/actions/reference/workflows-and-actions/variables#configuration-variable-precedence). Store workflow configuration variables at repository Actions scope and credentials in protected environment Secrets. Environment protections remain a separate owner configuration.
